# Autoland: a state-derived poller closes ADR-0024's deferred reject→re-queue loop — lander and fix runs on the run-token boundary, native forge reviews as the observable states, forge-only and default-off

ADR-0024 shipped `labctl pr merge` and, in its own status line, deferred "the reject → re-queue loop and `pr close`/`pr comment`". So landing a claim PR is human-gated today: the **land-pr** skill validates an open PR — checks, conventions, conflicts — and merges it once the operator confirms in free text. Autoland closes that deferred loop without a human in the middle. A **lander run** validates a claim's PR and merges, approves, or rejects it; on a rejection a **fix run** re-engages the same claim branch, carrying the rejection's findings back as new information. No new road to the forge is built — every write still rides the run-token agent surface exactly as `pr merge` does (ADR-0014), and the engine decides what to spawn by reading forge PR review state plus the runs store (ADR-0015, poll-only), never by dispatching a message. This ADR ships the review verbs, their seam, and the shared validation definition (issue #180); the poller/lander engine (#181) and the fix-forward loop and escalation (#182) land behind them.

The pins, decided:

- **PR review verbs on the run-token boundary.** `labctl` grows `pr reject <n> <body>` (a Forgejo-native *changes-requested* review, the findings carried as the review body), `pr rerequest <n>`, `pr approve <n> [body]`, and `pr comment <n> <body>`; `pr view` surfaces each review's state and body. Every verb is wired exactly like `pr merge` — a `Tracker` seam method → the run-token agent API → `labctl` — repo-scoped by the run row, the run token's repo scope the only boundary (ADR-0014). A forge that refuses a review surfaces its own words verbatim as `tracker.ErrReviewRejected` → a 409 with a non-zero `labctl` exit, mirroring ADR-0024's `ErrMergeRejected`. The **builtin** binding defers reviews entirely: review listing is empty and every review write returns `tracker.ErrUnsupported` — autoland is forge-only for now. The observable states of the loop are **native forge reviews** — not labels, not comments-as-protocol — so a human's own *changes requested* review feeds the very same loop a lander's rejection does.

- **State-derived, poll-only (ADR-0015 stands).** What to spawn next is a pure function of two already-polled facts: the forge's PR review state and the runs store. No webhooks, and no dispatch or queue message between the engine and a run — the same one-reaper, one-contract polling model every binding already runs under. (The engine that computes this is #181; this ADR pins the contract it reads, not its code.)

- **Two run kinds, each with an explicit forge-observable done-signal.** The **lander run**'s done-signal is its verdict landing on the forge — a merge, an approving review, or a changes-requested review. The **fix run**'s done-signal is an explicit `labctl pr rerequest <n>` — symmetric with `pr create` as the AFK run's done-signal, and deliberately *not* PR-existence: a fix run works a claim whose PR already exists, so "a PR is open" would read as done the instant it started. The done-signal has to be the thing the run does when it is *finished*, which for a fix run is handing the PR back for re-review.

- **Lander verdicts map to forge actions.** A clean **PASS** with `auto_merge` on → merge. A **PASS with CONCERNS**, or a clean PASS with `auto_merge` off → **approve only**, the approving review being the forge-observable "validated, awaiting the operator's confirm". A **FAIL** or a blocking CONCERNS → **reject**, the findings written as the changes-requested review body. Trivial fixes the lander makes inline on the claim branch; substantive ones it bounces to a fix run rather than rewriting another run's work itself. The PASS/CONCERNS/FAIL rubric — and the checks verdict it folds in (ADR-0032) — is the validation core's, not the lander's to redefine.

- **The attempt bound counts fix-run spawns per PR, default 2 — never rejection reviews.** A dead or crashing fix run posts no review, so bounding on rejection-review count would let a fix run that never produces one respawn forever. Counting spawns makes every attempt — including the ones that die on the launch pad — burn down the budget.

- **Escalation is agent-executed and terminal.** When the attempt bound is spent, an **escalate-mode lander** posts the digest comment, flips the issue to `ready-for-human`, and sends the push notification — all on the run-token boundary. The engine itself never writes to a forge; keeping the escalation writes agent-side is what keeps that invariant intact. Re-entry after escalation is a manual, human decision.

- **Per-repo settings, default OFF.** `enabled`, `max_fix_attempts`, `auto_merge`, and `lander_provider`, all per-repo — autoland is opt-in, never a thing a repo gets by upgrading. A fix run inherits its authoring run's provider; the lander runs under `lander_provider`.

- **Fix-forward, not auto-requeue.** A fix run is *bounded re-engagement carrying new information* — the rejection review — onto the existing claim branch. That is categorically not the blind retry the avoid-list forbids: auto-requeue re-runs the same issue from scratch with nothing learned, and it stays rejected (twice over now). The distinction is the new information; a re-engagement carrying none is auto-requeue by another name.

- **One validation core, shared by skill and lander.** The definition of *landable* — the checks gate, the convention checks, the conflict policy, and the PASS/CONCERNS/FAIL rubric — lives in `assets/skills/land-pr/validation-core.md`, seeded into every worktree with the land-pr skill (ADR-0012/0035) and referenced by both the interactive **land-pr** skill and the future lander seed template. One definition, one place, no drift between the human-confirmed path and the autonomous one.

## Status

Accepted. Completes the deferral in ADR-0024's status line (the reject → re-queue loop and `pr comment`, now shipped as native review verbs). Lands in three stages behind one contract: #180 the review verbs, the docs, and the validation core; #181 the state-derived poller and the lander; #182 the fix-forward loop and escalation. Rides ADR-0014's run-token boundary (the review verbs join `create | view | list | merge | checks`), keeps ADR-0015's poll-only model (no webhooks, no dispatch), and folds ADR-0032's checks verdict into the validation core's PASS/CONCERNS/FAIL rubric. The builtin binding's review ops are deferred; autoland is forge-only until they land.

## Considered options

- **Webhooks to deliver a rejection.** Rejected: ADR-0015 pinned lab to polling — one reaper, one contract across every binding — and autoland reads the same forge state on the same ticks. A push model is a separate, larger change and buys nothing the poller cannot already see.
- **A dispatch or queue message from the engine to a run.** Rejected: the spawn decision is derived from forge review state plus the runs store, and that state survives a restart where an in-flight message would not. State-derived is re-entrant by construction; a message bus is one more thing to lose.
- **Bounding on rejection-review count instead of fix-run spawns.** Rejected: a fix run that dies or crashes posts no review, so a rejection-review bound never counts it and it respawns without end. The spawn is the thing that must be budgeted.
- **Engine-executed escalation writes.** Rejected: the engine never writes to a forge — the whole agent surface exists so that forge writes ride the run-token boundary (ADR-0014). An escalate-mode lander keeps the digest comment, the `ready-for-human` flip, and the push on that boundary.
- **Auto-requeue / blind retry of a rejected PR.** Rejected — again. Re-running an issue from scratch with no new information is the runaway-cost nightmare the avoid-list has rejected twice; fix-forward differs precisely by carrying the rejection review forward, and the blind form stays forbidden.
- **Default-on.** Rejected: autoland merges code without a human confirm, so it is per-repo opt-in — a repo turns it on deliberately, never by upgrading into it.
- **Reviews on the builtin binding.** Deferred: the loop's observable states are native forge reviews, and the builtin tracker has no review object yet; its review writes return `tracker.ErrUnsupported` and autoland stays forge-only until it grows one.
