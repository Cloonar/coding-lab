# Repositories redesign: a status list with Needs you, a repo home with readiness, repo settings on one page with one save bar, and Run now for Schedules

The Repositories page was one card per repo, the shape ADR-0025 gave it when the dashboard's repo cards moved to `/repos`. A card's head row held the name and Stop all, Issues, CRs and Settings as text links, which wrapped on a phone. Chips showed the tracker binding, Incogni and the clone status, and parked work was listed inside the card. Live runs, the ready queue and the AFK state were not visible, and the cards had no meaningful order. There was no repo home: the breadcrumb's repo segment pointed at Issues, and the AFK strip only existed under the New-run composer.

Repo settings had the layout issue #198 introduced, which no ADR recorded: a category index on phones and a master-detail split from 1024px, in data-model order. Each section was its own form with its own Save at the end, errors appeared in a banner at the top of the section, and leaving with unsaved changes asked through a browser confirm. No value was visible before a section was opened. Overridable fields explained inheritance in hint text and had no way back to inheriting. Container limits stayed editable on the `host` Runner, and Autoland's options stayed visible with Autoland off. A Schedule was edited in a form inside its list row, was deleted through a browser confirm, and could not be started on demand. Deleting a repository was a browser confirm whose force option appeared only after a refused attempt, and a repo that other repos import was refused only after the click.

The maintainer reviewed three mockups and chose direction A, "Single scroll", then approved a second round that carries every detail (issue #61; the mockup is `docs/reference/repo-settings-mockup.html`, and screenshots of the built views at 390px and 1280px are in `docs/reference/repo-settings-screenshots/`). The maintainer also decided that all of it lands as one change. This ADR records what that supersedes and the two server additions it needed: starting a **scheduled run** on demand, and a **readiness** report per repo.

The decisions, pinned:

- **Repositories is a status list.** One row per repo, and the whole row opens the repo home. A row shows the name (Incogni as a chip beside it), the remote as host plus path, and the repo's state: live runs with the count waiting for the operator, the **claimable** count, the AFK state (Auto on, off, or paused) and Autoland. Below 1024px a row stacks name, remote and one status line. From 1024px the same data is a table with the columns Repository, Runs, Ready, AFK, Autoland and Last run. The order is latest run first, by the repo's existing `last_opened_at`, followed by the repos that never had a run, newest first. A filter field narrows the list by name or remote as the operator types. A cloning repo shows its progress in its row. A count lab does not know yet is a dash, never 0. Stop all, parked work and the Issues, CRs and Settings links leave the list; Add opens Add repository.

- **A Needs you block sits above the list.** It lists every repo with a failed clone (action: Retry), a **three-strikes pause** (action: Reset), or a failing readiness check (action: Fix, which opens the offending field). The block is absent when nothing qualifies and hidden while a filter is active. Every repo response now carries a `summary`: the claimable and open-issue counts as last known (null when not known yet) and the readiness report. The block and the Ready column therefore need no request per repo, and none to a forge.

- **`/repos/:id` is the repo home.** It shows a back link to the list, then the name, the tracker binding chip, the clone state when not ready, and the remote. Its tabs each have their own URL: Overview, Issues with the open count, CRs for builtin-bound repos only, and Settings. The existing Issues, issue detail, New issue, labels, CRs and CR detail routes render inside the frame unchanged, so every deep link keeps working. Builtin-bound repos get the CRs tab because **change requests** are the builtin tracker's counterpart to the forge's pull requests, and the list no longer carries a CRs link. Inside the frame the header and the back link name the repo, so the breadcrumbs start at the tab. Every link that means "this repo", the Chat header's project link among them, points at the repo home instead of at Issues.

- **Overview gathers what the cards held, plus what they lacked.** Readiness comes first. Then Live runs lists the repo's live instances with their **conversational state**, each linking to its Chat, with Stop all asking in place before it acts. The existing AFK strip follows (claimable count, Run one, the Auto switch, the three-strikes Reset), and the strip under the New-run composer stays. Last comes the **Parked view** with its per-entry Discard, which also asks in place. Until the clone is ready, Overview shows only Readiness.

- **Repo settings are one page, ordered by how often a section is touched.** All ten sections render on one page in four groups: Runs (Agents, Runner), Automation (Autoland, Schedules), Access (Secrets, Imports), Setup (General, Integrations, Branches), then Danger zone. Set-once sections come last, not the data model's order. Below 1024px a sticky row of section chips sits under the tabs, marks the section in view, and jumps on tap. From 1024px a sticky outline with the group labels replaces it. `/repos/:id/settings/:section` keeps working for every existing slug and opens the page scrolled to that section. Every field stays; the Agents section groups its fields as "Runs you start", "AFK runs" and "AFK capacity", and the AFK option bag, the seed prompt's Customize action and its done-signal hint stay inside "AFK runs".

- **One save bar for the whole page.** Fields wait for Save. A save bar appears while at least one field differs from the saved repo. It shows the count of changed fields and the names of the changed sections as links that jump there, and offers Discard and Save. Save sends one repo PATCH carrying the changed fields of every section. A changed field is marked at its label, and a section with changes is marked on its chip and in the outline. Discard restores the saved values and offers Undo for a few seconds. A Save button per section made the operator scroll to the end of each form and gave no overview of pending changes; one bar makes the page's pending state one fact. The pending changes live at the repo home frame, so the bar stays visible on the Overview and Issues tabs of the same repo. Leaving the repo with pending changes opens an in-page dialog (Keep editing, Discard, Save and leave); a tab close or reload keeps the browser's own prompt. The Auto switch on Overview still applies at once. The Auto-spawn field in Settings waits for Save, and it follows a change made on Overview unless it holds an unsaved edit.

- **Errors land at the field.** The browser checks that the name and the default branch are not empty, that the **AFK** branch pattern contains `<N>` exactly once, that the manual branch prefix is not empty, and that numeric fields are whole numbers. A problem appears under its field, the save bar shows the number of problems and the sections they are in, and Save scrolls to the first problem and focuses it without sending anything. Repo PATCH and create refusals now name the offending JSON field, as `{"error": "<message>", "field": "<json key>"}`, so a server refusal is shown at that field too. A refusal that names no field is shown in the save bar.

- **Rows that act at once are tagged, not converted.** Schedules, Secrets and Imports are lists of independent objects, each with its own server call. Their sections carry an "applies immediately" tag in the heading and keep acting at once. Folding them into the page's save would invent a transaction the server does not have: one Save that could create a Schedule, fail on a secret and leave the operator to work out which half happened.

- **Reversible actions apply at once and offer Undo; irreversible ones ask in place.** Removing a read-only import applies at once and offers Undo for a few seconds. Deleting a secret or a Schedule, Stop all, a parked Discard and deleting the repository ask in place first. No browser confirm remains in the repo list, the repo home or repo settings.

- **Inheritance is shown per field, and resolved by the server.** Every overridable field says "inherited" or "set here" at its label. An inherited field shows the value it resolves to, as the first pick of a select or the placeholder of a text or number field. A field set here shows the value it would otherwise inherit, and a Reset that returns it to inherited; Reset counts as a change, waits for Save, and is saved as a null override. Remote control, both the manual and the AFK field, becomes a three-way control (inherit, naming what it resolves to; on; off), and off is saved as an explicit `false`, never as null. The inherited values come from `POST /api/v1/repos/{id}/inherited`. For each overridable field it runs the very resolver the spawn path calls (the chains of ADR-0021, ADR-0030, ADR-0045 and ADR-0071) on a copy of the repo with that one field nulled. The browser never derives an effective value a second way, so the page and the spawn path cannot drift: there is one chain to drift. It is a pure read, with no write, no network call and no process.

- **The inherited endpoint is a dry run with drafts.** Its body may carry unsaved values of the fields other chains read: `provider`, `model_default`, `effort_default`, `remote_default`, the three AFK defaults, `lander_provider` and `lander_model`. A dependent field's inherited value then follows an edit above it before anything is saved. Pick another agent, and the inherited model is the new agent's, not the saved one's. Without drafts the page would show stale inherited values until Save, or compute them itself, which is the second derivation this rule forbids.

- **Only what applies is shown, and folding never changes a value.** With the effective Runner `host`, the dev image and the container limits fold into one note saying they apply to container runs only. "Show anyway" unfolds them, because staging a value before switching the Runner is legal, and the host warning shows whenever the effective Runner is `host`. With the builtin tracker binding, the forge credential field is replaced by a note, and the Autoland section says why it is unavailable, links to the tracker binding field and disables its switch. With Autoland off, the merge policy, max fix attempts and lander fields are replaced by a note.

- **A Schedule opens in an editor at its own URL.** The Schedules section lists each Schedule with its name, its cadence in words, its flows, the next run and the last outcome. A paused Schedule shows a chip and Re-enable, and every other row has an enabled switch that applies at once. Activating a row opens the editor at `/repos/:id/settings/schedules/:scheduleId` (`…/new` for a new one): full screen with a back control below 1024px, a side panel over the settings page from 1024px, closed by Browser Back. It holds every field of the old editor, the prompt Examples pick, and the server-rendered preview of the next runs for every cadence mode. It has its own Save; closing it with unsaved edits asks in place, and Delete lives in it and asks in place. The Schedule JSON gains `next_run_at` and `next_run_display` (the next cron match from the same parser the preview uses, null when switched off, paused or unparseable) and `last_run` (the newest run with that `schedule_id`), so the list never computes cron in the browser either.

- **Run now starts a scheduled run on demand — amending ADR-0062.** The button lives in the editor. It uses the saved Schedule, so it is disabled while the editor has unsaved edits and absent for a Schedule that was never saved, and the confirmation after a save offers it. `POST /api/v1/repos/{id}/schedules/{sid}/run` answers 202 with the run, or a 409 with the reason, which the UI shows verbatim. The run is an ordinary scheduled run: the same prompt and flows, the same overrides, the same **budget clock**, the same failure accounting. Its `kind = 'scheduled'` and `schedule_id` attribute it to its Schedule exactly like a cadence firing, and it appears in the runs rail like any live run. A Run now run that dies strikes that Schedule's own consecutive-failure counter and never the repo's three-strikes counter, and a repo paused by AFK three-strikes does not block Run now (ADR-0062's independence, unchanged).

- **Run now is a candidate for the one spawn pass, never a second launch path.** The request runs one synchronous **spawn pass** with a single on-demand candidate at the scheduled stage rank, appended after every producer's candidates. The pass stays the only consumer of the instance cap (ADR-0049); a button that launched directly would be exactly the cap race that ADR removed. The candidate competes for a slot in pipeline order like any firing: behind lander and fix runs, ahead of new AFK work. Being appended last is load-bearing. When the same Schedule's cadence slot is due in that very pass, the stable sort launches the cadence firing first, and the Run now then meets it as a live previous run. The reverse order would overlap-skip the cadence firing and consume it. The pass is a full one, so it may also launch other due candidates on its way, and the request waits for it, because the answer is the pass's verdict.

- **A refused Run now is refused, never queued.** All refusals are 409s with a fixed reason. The issue named three (paused, previous run live, the cap); the other four stop a launch that would fail or waste its budget. In order of precedence:
  - the Schedule is paused by its own three-strikes ("schedule is paused after consecutive failures — re-enable to re-arm");
  - the repo's clone is not ready ("repository is not ready");
  - its previous run, cadence or Run now, is still live ("schedule's previous run is still live");
  - the prompt and flows compose to nothing ("schedule composes an empty prompt — check its prompt and flows"), reachable only through a stored row whose flows this binary no longer knows;
  - the Schedule already started a run this minute ("schedule already started a run this minute — try again in a minute");
  - the provider is logged out ("provider is logged out"), checked with a forced login check per click, because a spawn while logged out would die at the login wall and strike the Schedule for nothing;
  - the repo is at its instance cap ("instance cap reached").

  The first four are checked before the pass, in the order the locked launch checks them, re-checked under the engine lock, and checked once more when the pass's snapshot vetoes the candidate at the cap, so the specific reason wins over the cap. A refusal that queued would be a firing waiting behind another, which Schedules never do: ADR-0062's skip-on-overlap rule exists because pending firings stacked behind a slow run are runaway unattended cost.

- **Run now works on a switched-off Schedule and leaves the cadence alone.** The enabled flag gates only the cadence, so a prompt can be tested before the cadence is armed. Paused still refuses: a struck-out Schedule waits for its human re-enable either way. Run now never reads or writes the in-memory cadence memo (the pending firing and the evaluation high-water mark), and never stamps `last_fired_at`, which stays "the last cadence firing", the startup missed-slot log's baseline. It neither moves nor consumes the next cadence firing by bookkeeping.

- **A live Run now run is "the previous run".** Skip-on-overlap is unchanged and applies to it. A cadence slot that comes due while a Run now run is live is skipped and consumed, logged loudly like any overlap. With the default 30-minute budget, a Run now shortly before a slot costs that slot. The reverse also holds: a live cadence run refuses Run now. Exempting Run now runs would mean two live runs of one Schedule, which is the stacking ADR-0062 rejected.

- **The same-minute refusal, and why the label grammar stays.** Scheduled-run labels are minute-granular: `sched-<id-suffix>-<yyyymmdd-hhmm>`, pinned by ADR-0062, and the branch is the repo's manual branch prefix plus that label. A cadence can never collide with itself, since cron matches once a minute and a Schedule has one live run. A Run now can: Run now, a **neutral Stop** (which keeps the branch) or a death that leaves an unmerged branch, then Run now again inside the same minute would reuse the session, branch and worktree names, and git would refuse the branch mid-launch with a 500. So the on-demand path checks the Schedule's newest run row and the branch in the **reference repo** before anything is created, and refuses with "try again in a minute". The grammar is not made finer. Reconciliation derives a scheduled run's branch from that label for restart re-adoption and **parked work**, and every existing scheduled branch carries it. A second grammar, or a counter, would change that identity for an edge one minute wide. A minute of "try again" costs less.

- **Readiness answers whether a run can start in this repo right now.** The report is an ordered list of up to six checks: clone, git credential, tracker, agent login, dev image (only while the effective **Runner** is `container`, or failing when the effective Runner cannot be resolved at all), and read-only imports. Each check is passing, failing or pending, carries a one-sentence detail, and offers at most one remedy: retry the clone, or the settings field that fixes it (a repo settings section and field, or the Credentials page for an agent login). The roll-up is failing over pending over passing. On Overview, all checks passing collapse to one line, "Ready to run". Any failing or pending check opens the block, failing checks first, and while a clone runs the block shows its progress and says runs can start when it finishes. The report is `GET /api/v1/repos/{id}/readiness`, and the same report rides every repo response's summary.

- **Readiness is built only from what lab already holds.** That means the repo row, local configuration checks, and the outcome of operations lab performs anyway. The tracker binding is validated locally, without a request, and the container spawn gate, with its in-memory preflight verdict, is the very verdict a spawn is refused by. In-memory recorders keep the outcome of the most recent credentialed fetch (behind every launch, `/pull-base`, a change-request merge, a completed clone), the last definitive forge list reads (ready queue, issues, pulls), the claimable count whenever something computes it, and the spawn-time pull-if-missing of the dev image. Each provider's last known login state is read through the new optional capability below. A page view causes no forge request, no git network operation, no provider CLI process and no podman process, and a test pins that. The list shows fifteen or more repos: a check that called the forge for each would make the page slow and spend API quota on every view.

- **A check lab cannot evaluate is left out, never shown as passing.** There is no "unknown" state. A git credential with no fetch recorded since boot, a forge tracker with no read under its current credential, an agent whose login was never successfully checked since boot, and a dev image never ensured since boot all leave their check out of the report. A passing check would claim something lab never observed, and an "unknown" line in every report after a restart would be noise the operator cannot act on.

- **The recorders live in memory, and a restart empties them.** Right after a restart most checks are absent. They return as lab's own work (a launch, an engine pass, a fetch) records outcomes again. The issue set memory as the bar, and a record persisted across a restart would describe a world that may have changed while lab was down. No record, no verdict.

- **Fetch attribution is opt-in per call.** Only callers that fetch with the repo's own git credential attribute their fetch, and an unattributed fetch is never recorded. The reconcile sweep fetches every repo with no credential at all and fails on every private remote by design, so recording it would turn each sweep into a false "credential broken" verdict. A caller that forgets to attribute only withholds evidence; it can never plant a wrong one. A fetch whose caller's context is already done (a dropped request, a forced delete cancelling the clone, shutdown) is not recorded either, and neither is one that failed on a lock in the local repository (`cannot lock ref`, a `.lock` file in the way). Fetches are not serialized per reference repo, so an attributed fetch can lose a ref lock to the sweep's; the lock is the local repository's, and says nothing about the remote or the credential.

- **Only a definitive tracker answer is evidence.** A list read is recorded when it succeeded or when the forge refused it about the token or the repository: a 401, a 403 that is not a rate limit, or a 404, which both forge clients classify as `tracker.ErrAccessDenied` and `tracker.ErrNotFound`. A 5xx, an unreachable forge, a timeout or a rate limit is not recorded and never overwrites a record: the forge did not answer the question, and the condition heals by itself.

- **A record goes stale with its credential.** Each record carries the stamp of the credential it was observed with (its id and its last update). Once the repo points at another credential, or that credential is rotated or renamed, the record no longer counts and its check is left out until a fetch or read under the new one records an outcome. `repo.changed` is published only when a verdict or a count changes, never per read, for every repo that reads the changed record: a flipped fetch verdict also announces the repos that import the fetched repo, and a flipped dev-image verdict announces every repo on the `container` Runner (or whose Runner cannot be resolved), a few repos too many rather than one left stale.

- **A summary that cannot be computed degrades the response instead of failing it.** The repo is answered with what its row alone decides: both counts null and only the clone check. Most repo responses follow a write that has already committed, and a 500 would tell the operator a saved change failed; the list likewise never empties over one failed read.

- **Providers gain an optional `AuthPeeker` capability.** `LastAuthStatus()` returns the status the most recent completed login check produced, however old, and whether one has completed at all. A check that failed (the status command missing, its output unreadable) or was cut off by its caller's context never moves it: its logged-out stand-in is a spawn-safety default, not evidence of a logout, and an operator leaving the Credentials page mid-check must not turn every repo's agent check red. It never runs the status command, never refreshes the cache, and never blocks behind a check in flight. `AuthStatus` stays right for a spawn decision and the login card, but it may start a process, and on a container-mode server a podman container (ADR-0057). That is far too much for a report read with every repo list. Both shipped adapters and the `providertest` fake implement it. It is advertised by type assertion like `DeepLinker` and `ConnectingReporter` (ADR-0017), and a provider without it simply has its agent login check left out.

- **Deleting a repository stays in Danger zone only, and its dialog states what will happen.** The maintainer declined a second entry point on the list or the repo header. The button opens an in-page dialog, a bottom sheet below 1024px and a centered dialog from 1024px. It lists only the consequences that apply to this repo, with counts. Live instances will be stopped, and a running clone abandoned. Parked branches go with lab's clone, while their worktree folders stay on disk, because the server never removes them. Schedules and secrets are deleted with the repo row, along with its settings and run history and, on a builtin-bound repo, the built-in tracker's issues and change requests. The remote is not touched, and the action cannot be undone. A count the dialog could not load is left out, never shown as 0. The operator types the repo name to enable Delete. With live instances or a running clone, confirming sends the forced delete at once: the operator has just read that consequence, so no second attempt is needed.

- **Importers are known before any attempt, and checked before any forced side effect.** `GET /api/v1/repos/{id}/importers` lists the repos that import this one. When there are any, the dialog names them, offers no way to delete, and links to the first importer's Imports section. On the server, repo delete now checks importers first, before a forced delete cancels the clone or stops instances. It used to tear the repo's work down and then refuse anyway. `force` still never bypasses the refusal (ADR-0063), and the store keeps its own check as the backstop for an import declared in between. After deletion the app returns to the list and confirms with the repo's name.

- **Add repository drops the Agent pick.** The form holds the remote URL, the name, the git credential, the tracker binding (Auto, Forge, Built-in), the forge credential (hidden for Built-in) and Incogni. A new repo inherits the global default agent like every other overridable field, and the pick stays available in Settings → Agents. The name is filled from the URL as the operator types and stays editable; once edited, it is no longer overwritten. Errors appear under the field, a server refusal at the field its key names. After creation the app opens the new repo's home, whose readiness block shows the clone progress, instead of the New-run composer.

- **No new dependency, no new design token, no new font.** The existing tokens, the vendored icon set (ADR-0019) and the existing form components cover the design, with a few shared controls added: a switch, a segmented control, an in-place confirm, a dialog that is a bottom sheet on phones, and a toast with an action for Undo. The provider-neutral guard still applies: the UI uses the provider's display name and catalog, never a hardcoded agent or model name.

## Status

Accepted 2026-10-05. Resolves issue #61, the GitHub issue; the "issue #61" ADR-0029 cites is an older number from the Forgejo tracker.

- **ADR-0025:** supersedes the repo cards it re-homed to `/repos` (one card per repo carrying clone status and progress, Stop all and parked work). `/repos` is now a status list with Needs you, and those controls live on each repo's home. The runs rail, the composer-first Home and the AFK strip under the composer stand; the strip now also appears on Overview.
- **Issue #198's repo settings layout**, which no ADR recorded: supersedes, for repo settings only, the category index on phones, the master-detail split from 1024px, the data-model section order, the per-section Save, the section-level error banner and the browser-confirm leave guard. **Global Settings keeps all of that layout and its per-section save**: only the per-repo area changes. The section slugs stay.
- **ADR-0062:** amended by Run now. A Schedule can also be started on demand, through the same spawn pass, refused (never queued) while paused, while its previous run is live, at the cap and in the cases listed above. Run now works while the Schedule is switched off and never touches the cadence's state. Skip-on-overlap now also consumes a slot that comes due during a live Run now run. The cadence, no catch-up, the label grammar, the per-Schedule three-strikes and the single push trigger stand.
- **ADR-0049:** extended. A candidate may be handed to the pass on demand, appended after the producers' candidates; the pass stays the sole consumer of the cap.
- **ADR-0063:** the importer refusal now comes before a forced delete's teardown. The rule itself, that `force` does not bypass it, stands.
- **ADR-0017:** extended with the optional `AuthPeeker` capability.

`CONTEXT.md` gains **Readiness**. **Schedule**, **Scheduled run**, **Spawn pass**, **Parked work / Parked view** and **Read-only import** are amended. `docs/agents/provider-authoring.md` documents `AuthPeeker`.

## Considered options

- **The two other mockup directions: a summary index with edit sheets, and a control panel with quick toggles.** Rejected by the maintainer, who chose direction A and approved its second round. The other two are not to be blended back in.
- **A second delete entry point, on the list or in the repo header.** Declined by the maintainer: Danger zone stays the one place to delete a repository.
- **Fold Schedules, Secrets and Imports into the page's save.** Rejected: it would invent a transaction the server does not have. The tag tells the operator these rows act at once.
- **Derive inherited values in the browser from the settings it already loads.** Rejected: a second resolution chain beside the spawn path's, which drifts the first time either changes. The server answers with the spawn path's own resolvers, drafts included.
- **Split the work into several pull requests.** Rejected by the maintainer. The work replaces one way of moving through repos and their settings with another, and a partial landing would leave the app with both.
- **Queue a refused Run now until it can launch.** Rejected: a queued Run now is a firing waiting behind another, which Schedules never do (ADR-0062), and it would launch later with nobody watching. The operator retries when the reason is gone.
- **Launch Run now directly instead of through the pass.** Rejected: a second launch path is a second cap consumer, the race ADR-0049 removed by construction.
- **Let Run now reset or advance the cadence (stamp `last_fired_at`, move the next firing).** Rejected: the cadence is anchored to the clock, not to the last run, and `last_fired_at` is the startup missed-slot log's baseline. Testing a prompt must not shift next Monday's firing.
- **Exempt Run now runs from skip-on-overlap.** Rejected: it would allow two live runs of one Schedule.
- **Make scheduled-run labels finer (seconds, or a counter) to avoid the same-minute collision.** Rejected: it changes an identity ADR-0062 pinned and reconciliation derives branches from, for a one-minute edge that a refusal covers.
- **Check readiness against the forge (and git, and the provider CLI) per page view.** Rejected by the maintainer: fifteen or more repos per list, a slow page, and API quota spent on every view. Lab's own work already produces the evidence.
- **Persist the readiness records.** Rejected: memory is enough, and a restart costs only a shorter report until lab's own work refreshes it.
- **Show a check lab cannot evaluate as passing, or as "unknown".** Rejected: passing claims something lab never observed, and "unknown" lines are noise the operator cannot act on.
- **Record every failed tracker read or fetch, transient ones included.** Rejected: one 502, timeout or lost local lock would fail the check and raise a Needs you entry, with a fix pointing at the credential, until the next read or fetch of that kind, over a condition that heals by itself.
- **Record every fetch, the reconcile sweep's included.** Rejected: the sweep fetches without the repo's credential and fails on every private remote by design, which would report a broken credential every few minutes.

## Consequences

- Loading the Repositories list or a repo home causes no forge request and no git network operation. A forge-bound repo's Ready count and Issues count show a dash or nothing until something lab does anyway (an engine pass, the composer's AFK strip, an issue list read) has computed them since boot.
- After a restart, readiness reports are short (often just the clone check, plus the tracker check of a built-in-tracker repo and the imports check of a repo that imports nothing) until launches, passes and fetches record outcomes again. A Needs you entry for a failing check disappears on restart for the same reason, and comes back with the next failing operation.
- A read-only import whose target is still cloning makes the imports check pending, with no fix: the state clears by itself, and removing the import is not its remedy. A failing target still outranks it.
- A new optional provider capability: an adapter without `AuthPeeker` gets no agent login check. Both shipped adapters implement it.
- A Run now shortly before a cadence slot costs that slot, and a second Run now within the same minute is refused with "try again in a minute".
- A Run now request holds the HTTP call for one spawn pass, including any other candidates the pass launches on the way. It runs on the server's own context, so a client hanging up does not abort a launch mid-way.
- Repo deletion with importers no longer stops anything before refusing. The dialog makes the refusal visible before the click, so the API refusal is now a backstop.
- `SettingsLayout` and `useSettingsForm` now serve global Settings only; the repo page has its own form store at the repo home frame, with one dirty state, one submit and one leave guard across all sections.
- `/repos/:id` is a page now; it used to match no route and fell through to the New-run composer. Old links to `/repos/:id/issues`, `/crs`, `/labels` and `/settings/:section` still resolve, inside the frame.
