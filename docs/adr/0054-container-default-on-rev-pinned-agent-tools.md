# Container-ready by default: `services.lab.container.enable` defaults on, agent-tools images release-tagged per lab commit, and the tools pull verified end to end — publish-side anonymously, host-side with retry

ADR-0052 shipped the container runner behind a deliberately explicit opt-in: every host mutation gated on `services.lab.container.enable = false` by default, and `toolsImages` empty with no default. That posture was right for the tracer bullet and wrong for the steady state, which the first real rollout proved (issue #220): the dev host took the module PR, CI bumped the pin, the deploy went green — and container spawns stayed refused, because nothing in that pipeline ever flips a switch that lives in a *different* repo's host config. An opt-in that every deployment is expected to take is not an opt-in; it is a deploy-time trap. And even a host that flips it then faces a second gap: nothing ties the agent-tools image (whose baked-in `labctl` speaks to this server) to the server's own code revision — the only published tags carried the *provider CLI* version, while `labctl` changes with every merge.

The pins, decided:

- **`container.enable` defaults to `true`: enabling lab means a container-ready host.** The provisioning stays gated on the one switch (never on option non-emptiness — that ADR-0052 rule is untouched); what changes is the switch's resting position. A host that must not run containers sets `enable = false` and gets the byte-identical pre-container unit — the zero-diff guarantee moves from "the default" to "the opt-out", and the `nixos-module` check pins it there. Consequence accepted deliberately: `virtualisation.podman.enable` is now on for every lab host, and an operator force-disabling podman without also disabling `container` surfaces as an eval conflict, which is the honest shape of that contradiction.

- **The agent-tools publish job release-tags every image with the lab commit: `<provider>-<git sha>`, pushed on every merge to main.** `labctl` is compiled from the repo tree *inside* the image build, so image content was always a function of the lab rev — the tag set just failed to say so. The `<provider>-<cli-version>` tag stays (human-facing: which CLI is inside); the sha tag is the code pin. The publish leg's `containers/**` path gate is dropped (the PR smoke leg keeps it): a path-gated release leaves the sha tag dangling for any merge that touches only Go or web code — which is precisely the merge that changes `labctl`. The CI cost of building two images per merge is the price of the guarantee; the registry cost is small because the CLI layers are content-addressed and only the labctl layer churns.

- **The module's `toolsImages` defaults to the sha-tagged refs of its own flake rev.** `services.lab.container.toolsImages` defaults to `<toolsImageRepo>:claude-<self.rev>` / `:codex-<self.rev>` (`toolsImageRepo` is a new option, default `git.cloonar.com/cloonar/agent-tools`). A deployment pinned to rev R therefore runs, inside every container pane, the exact `labctl` built from R — the pin update that ships the server ships the matching agent surface, with no operator hand-off between the two repos. A revless source (dirty working tree: `nix flake check`, a mid-hack `nixos-rebuild --flake .`) has no sha tag to name, so the default falls back to the CLI-version tags from `versions.env` — a slightly stale labctl beats an eval failure exactly where determinism matters least. The sha *tag* rather than a digest is deliberate: the digest does not exist at eval time (the image is published by CI after the commit exists), and the digest remains the documented strict contract for hand-set refs.

- **"Can the image actually be pulled" is verified at both ends.** Publish-side: after pushing, the job logs out, then pulls the sha tags back into a scratch storage root and compares digests — *anonymously*, because anonymous pull IS the deployment contract (the module provisions no registry credentials), and Forgejo package visibility follows repo/org settings, so a package quietly flipped private would pass the authenticated push and then fail on every host. Host-side: preflight already resolved every configured ref at startup (`podman image exists`, else one pull); what is new is the **retry**. The deploy pipeline and the agent-tools publish trigger on the same push, so a freshly-deployed lab routinely races the publish of its own tools tag; a startup-once preflight would refuse container spawns until someone restarted the service. cmd/lab now re-runs preflight on an interval while a tools-pull failure is present — the one failure class time heals; every other check reports host state only a redeploy changes — republishing each verdict through the existing atomic gate, so spawns unblock the moment the registry serves the ref. Repeat verdicts log only on change: a steady outage is one warning, not one per minute.

- **The subid default is unchanged and the collision risk is documented, not detected.** Default-on means the `100000:65536` range now lands on hosts that never thought about subids — and `100000` is also the range most tools hand a host's first interactive user. Overlap is functionally harmless for podman but weakens the isolation story (two users' containers sharing host uids), and neither NixOS nor lab can reliably detect it at eval (auto-allocated ranges materialize at activation). The escape hatches stay as ADR-0052 built them: override `start`/`count`, or `subIdRange = null` and bring your own entries; ops.md now flags the check explicitly.

## Status

Accepted. Settled via issue #220 (2026-07-24), after the 2026-07-23 dev-new rollout diagnosis showed a pin bump alone can never activate the runner. Amends ADR-0052 (the enable switch's default and the preflight's retry behavior; the gating rule, mount inventory, argv, and refusal semantics are untouched) and ADR-0051 (adds the sha tag lane to the publish contract; the `/opt/lab` injection contract and digest-pinning discipline are untouched). ADR-0053's "defaultImage may be null" stands — this ADR adds no dev-image default.

## Considered options

- **Keep opt-in and document the host-config step harder.** Rejected: the failure mode was not missing documentation but a cross-repo seam — the repo that merges container support cannot flip the switch in the repo that deploys hosts, so "documented opt-in" structurally reproduces issue #220's silent no-op deploy. Defaults are the only channel this repo controls end to end.

- **Publish per-merge images but keep `toolsImages` defaulting to `{ }` with an eval assertion demanding refs.** Rejected: forces every deployment to hand-copy refs the flake can derive from its own rev — busywork that reintroduces the cross-repo hand-off, now on every pin bump instead of once, and drifts the moment someone forgets.

- **Default `toolsImages` to digest-pinned refs.** Rejected as impossible in the pleasant direction: the digest of a commit's image does not exist until CI publishes it, after the commit is already immutable. Committing the digest back would need a bot commit per merge (churn, races); the sha tag names the same content one metadata hop away, and preflight's pull plus the publish-side digest verification close the gap in practice.

- **A startup-once preflight with the race documented ("restart after deploys").** Rejected: the race is not occasional — deploy and publish share a trigger, so the *common* case for a freshly-deployed host is losing it. An operator instruction that must be followed after every deploy is an outage schedule, and the fix (re-run one idempotent check while its failure is the transient kind) is small and uses the gate exactly as designed.

- **Tagging with the lab release version instead of the git sha.** Rejected: the repo does not cut versioned releases — the deployable unit is a main commit, pinned by sha in the consuming flake (`deploy.yml` writes exactly that sha), so the sha is the identifier the whole pipeline already speaks.

## Consequences

- **A plain `services.lab.enable = true` deployment is container-capable after its first successful preflight** — podman, delegation, subids, runtime dir, and rev-matched tools refs all present with zero container config. Flipping a repo to `repos.runner = container` is now a UI action, not a host-provisioning project.
- **Host-only deployments become the explicit case**: `container.enable = false`, zero-diff guaranteed by the checks.
- **Every merge to main publishes images.** CI runs the agent-tools build+smoke+publish on every merge (previously only on `containers/**` changes). A registry-side failure there now blocks the "deployment is self-consistent" story and should be treated as a broken build, not an optional lane.
- **The agent-tools package must stay publicly readable.** The publish job's anonymous re-pull enforces it loudly; making the package private breaks every host's preflight by design (credentialed pulls are a deliberate non-feature until something needs them).
- **Existing hosts pick up podman and subid ranges on their next deploy.** Operators with pre-existing subid allocations (or force-disabled podman) must reconcile once — override `subIdRange`, or set `container.enable = false`.
