# An AFK run's claim is its afk/<N> branch, not a tracker label

ADR-0007 settled that `lab` selects, claims, and owns the lifecycle of an **AFK run** (see CONTEXT.md); the spawned agent only resolves the issue. It also picked the *mechanism* for the claim: `lab` flipped its chosen issue's label `ready-for-agent → in-progress` before spawning, so the queue query (`--labels ready-for-agent --state open`) excluded it for free. This ADR keeps everything in ADR-0007 except that mechanism. The claim is now the existence of the run's local `afk/<N>` branch — a durable artifact `lab` already creates — and `lab` reads and writes **no** claim label at all.

The label was a shared, mutable tracker field, and that was the flaw: any other actor could overwrite it. The `triage` skill (or a human) re-applying `ready-for-agent` to an already-claimed issue silently un-claims it. Worse, a failed run keeps its `afk/<N>` branch and worktree for inspection; if `ready-for-agent` is then re-added — the obvious "requeue" move — the next scheduler tick flips the label to claim the issue, the worktree-add fails because `afk/<N>` already exists, the rollback flips the label back, and the issue **flaps** `ready-for-agent ↔ in-progress` every tick while the real run is still working it. The claim and the queue label were two names for one fact living in a place neither `lab` nor `triage` exclusively owned, so they fought over it.

The `afk/<N>` branch has none of those problems. `lab` creates it as the run's isolated worktree, it is a local ref on disk (so it survives a `lab` restart with no extra bookkeeping and needs no tracker round-trip to read), and nothing in `triage` or a human's normal tracker workflow touches it. So we make the branch the single source of truth: issue selection lists the local `afk/<N>` branches (`git for-each-ref refs/heads/afk/`) and treats any open `ready-for-agent` issue that already has one as claimed, skipping it. Creating the branch *is* claiming the issue; tearing it down (a failed spawn's rollback, or a requeue) releases the claim. The label flip, the label-rollback, the `in-progress` label constants, and the `EnsureLabel`/`Relabel` tracker methods all go away.

The selection signal is the local branch and nothing else. A merged run closes its issue via `Closes #N`, so an open-state query excludes it regardless of the lingering branch; a failed or still-open-PR run keeps its branch, which parks the issue. We deliberately do **not** also consult the PR list in selection (the PR list stays the reaper's done-signal only): the one hole that adds — deleting an `afk/<N>` branch while its PR is still open — is operator error already forbidden by convention, and a branch-only rule is the simplest thing that is correct.

## Status

Partially supersedes [ADR-0007](0007-lab-drives-afk-runs.md): only its *claim mechanism* (the `ready-for-agent → in-progress` label flip and the rollback of it). The rest of ADR-0007 stands unchanged — `lab` still does the selection, the claim, and the lifecycle; runs are still reaped on a PR whose head is `afk/<N>` or on a ~2-hour timeout; a user Stop is still neutral; three consecutive failures still pause a project until a UI Reset.

## Considered options

- **Keep the `in-progress` claim label (ADR-0007 as-is).** Rejected: it is the source of the clobber and the flap. The claim lives in a tracker field that triage and humans also write, so coordinating them is a standing requirement, and a re-applied `ready-for-agent` on a parked failed run produces the per-tick flapping described above. The whole point of the change is to remove that shared mutable state.
- **Keep an advisory-only `in-progress` label that `lab` sets but never reads for selection** (selection keyed on the branch; the label is just a human-visible breadcrumb). Rejected: it buys tracker visibility back but reintroduces exactly the write `triage`/humans can clobber, and now the label and the branch can disagree (a human clears `in-progress` while the run is live, or it lingers after the branch is gone). Two records of one fact is the bug; a cosmetic second copy that can drift is not worth the confusion. If tracker visibility is wanted later, derive it from the branch/PR rather than from a separately-written label.
- **Select on the `afk/<N>` branch *and* an open PR** (exclude an issue that has either). Rejected as unnecessary. A merged PR closes the issue (open-state query excludes it); an open PR's run still has its branch (the branch already excludes it). The only case a PR check would catch that the branch does not is a branch deleted out from under an open PR — operator error the convention already forbids — and paying for it means coupling selection to a `tea pulls` round-trip on every tick. Branch-only is strictly simpler and covers every non-error case.
- **Auto-requeue a failed run** (e.g. delete its branch after N minutes). Rejected, same as ADR-0007 rejected auto-retry: a run that can't resolve its issue will keep failing, and silently re-claiming it forever is the runaway-cost nightmare. Requeue stays a deliberate human action — delete the `afk/<N>` branch and its worktree — and is unchanged by this ADR.

## Consequences

- `triage` and humans can freely (re)apply `ready-for-agent`; it can never clobber a claim or cause flapping, because the branch — not the label — is the source of truth. No coordination between `triage` and `lab` is required, and the canonical triage vocabulary loses a lifecycle label it never really owned.
- A failed run's surviving `afk/<N>` branch keeps its issue out of the claimable set (parked); the scheduler drains *around* it with no flapping, and the auto-loop's `(N ready)` hint and its launch predicate both count the *claimable* set (ready minus already-branched), so a project whose only ready issues are all parked reads zero and does not loop. Requeue is a single action: delete the `afk/<N>` branch (and its worktree).
- "What's being worked" no longer shows in the tracker. This is the accepted trade-off: it loses the tracker-visible "`in-progress` with no PR = failed run" signature, and the `lab` UI (which lists live runs, and against which orphan `afk/<N>` branches can be surfaced) becomes the sole dashboard. A separate follow-up may add a parked/failed-run view to that UI.
- The failed-spawn rollback gets simpler and fully local: tear down the worktree and delete the branch, with no tracker call to undo. A claimed-but-unlaunched issue still never strands, because the only thing the claim created was the branch.
- `lab` no longer needs `tea` label-write permissions for the claim (it still reads the issue queue and the PR list). The `land-pr` skill drops its "clear the `in-progress` label on merge" step; the success path is just the merge closing the issue via `Closes #N`.
