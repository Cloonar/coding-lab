# lab claims the issue and owns the AFK-run lifecycle; the agent only resolves it

> **Status:** the *claim mechanism* described below — the `ready-for-agent → in-progress` label flip and its rollback — is superseded by [ADR-0013](0013-afk-claim-is-the-branch.md). `lab` now claims an issue by creating its `afk/<N>` branch and writes no claim label. Everything else in this ADR still holds: `lab` does the selection, the claim, and the lifecycle; runs are reaped on an `afk/<N>` PR or a timeout; a user Stop is neutral; three consecutive failures pause the project until a UI Reset.
>
> [ADR-0017](0017-lab-per-instance-worktrees.md) supersedes the **consequence** below that *"ordinary human-driven instances are unchanged — they still share the project's main checkout."* Every instance — manual and AFK — now runs in its own worktree forked from `origin/<default>`. Teardown is one guarded rule everywhere: a manual instance's Stop, **and the AFK reaper on both success and failure**, remove a clean worktree (deleting its branch only once merged) and keep a dirty one whole — superseding the original behaviour where the reaper removed the worktree on success and kept it on failure. Startup reconciliation and a throttled runtime sweep apply the same rule to worktrees left by a crash and GC merged `lab/` and `afk/` branches, so a finished run's `afk/<N>` branch no longer lingers forever. The AFK-run *signals and accounting* are unchanged: runs are still reaped on an `afk/<N>` PR / death / timeout, the consecutive-failure counter still drives the three-strikes pause, and a user Stop is still **neutral** — it keeps the worktree and the `afk/<N>` branch so the claim/park ([ADR-0013](0013-afk-claim-is-the-branch.md)) survives, and is never counted as a failure.

An **AFK run** (see CONTEXT.md) is an unattended `lab` instance that takes one `ready-for-agent` issue from a project's own Forgejo tracker, resolves it, and opens a PR. This ADR settles how much of that workflow lives in `lab` versus in the spawned `claude` agent. The decision: `lab` does the issue selection, the claim, and the run's lifecycle management; the agent receives a specific issue number in its seed prompt and does nothing but resolve it and open the PR.

The forcing function is the *automatic* toggle. For auto-runs to be anything but wasteful, something must answer "is there a `ready-for-agent` issue right now that isn't already being worked?" *before* a run launches — otherwise auto would speculatively boot a full `--effort max` session just to discover there is nothing to do, and the manual "Start AFK run" button could never honestly disable. Only `lab` can answer that ahead of time, so `lab` already queries `tea`; once it does, having it also pick the lowest open issue number and claim it is a trivial increment — and it makes the claim race-free, because a single-threaded scheduler claims before spawning rather than two agents both `tea`-listing and grabbing the same issue in the gap before either relabels.

`lab` claims by flipping the label `ready-for-agent → in-progress` before it spawns the run (rolling the flip back if the spawn itself fails). The claim therefore lives in the tracker, where the queue query (`--labels ready-for-agent --state open`) already excludes it for free, it survives a `lab` restart with no extra bookkeeping, and a human reading the tracker can see what is being worked.

Because `claude --remote-control` is an interactive session that does **not** exit when its task is done — it opens the PR and then idles, holding its slot — `lab` cannot use "the session ended" as the done signal. Instead the scheduler treats *a PR whose head branch is `afk/<N>`* as done (matched client-side from `tea pulls list --fields index,head,state`) and reaps the run on that signal. A run that dies with no PR, or exceeds a ~2-hour budget, is a failure.

## Considered options

- **Let the spawned agent select and claim its own issue** (seed it a generic "find a `ready-for-agent` issue and resolve it" prompt). Rejected: `lab` is then blind to whether work exists, so the auto-toggle must speculatively spawn max-effort sessions that may find nothing, and the manual button can't disable honestly. It also reintroduces a real claim race — the gap between the agent's `tea` list and its relabel is the agent's whole startup-plus-reasoning window (seconds to minutes), long enough for two runs to grab the same issue. The only thing this buys is keeping `tea` out of `lab`; once the toggle forces `lab` to call `tea` anyway, that saving evaporates.
- **Claim with an in-`lab` "taken" set instead of a tracker label.** Rejected: the claim then lives only in `lab`'s state file, invisible in the tracker, needs explicit reconcile logic to survive a restart, and needs a release signal `lab` can't cleanly observe (the agent's success doesn't end the session). The label flip gets all of that from state the tracker already holds.
- **Run the agent headless (`claude -p`) so the process exits on completion.** Rejected: it discards the claude.ai deep link the whole `lab` UX is built on — you could not watch or take over an AFK run. Keeping `--remote-control` and reaping on PR-detected is the price of staying observable.
- **Auto-retry failed runs.** Rejected: a run that can't resolve its issue will keep failing, and retrying it forever is the runaway-cost nightmare. A failed run instead parks its issue in `in-progress` (out of the queue) and increments a per-project counter; three consecutive failures pause the project until a human resets it from the UI.

## Consequences

- `lab` now shells out to `tea` and needs `tea` credentials. The service runs as `dominik` with `HOME=/home/dominik`, so a one-time `tea login add` covers both `lab`'s issue queries and the agent's `tea pr create`; PRs and label edits are authored as `dominik`, not a dedicated bot.
- The feature only lights up on Forgejo-hosted projects (detected by an `origin` URL under `git.cloonar.com`, cached per path since remotes don't change). GitHub/GitLab clones in `~/projects/` show a disabled menu line — `tea` has nothing to target there.
- Each AFK run gets an isolated `git worktree` on a pre-created `afk/<N>` branch so it can't corrupt a concurrent manual session's (or another run's) working tree. The worktrees live under `~/.local/state/lab/worktrees/`, deliberately **outside** `~/projects/`: a worktree carries a `.git` *file*, which `lab`'s scanner (`hasGitMarker`) matches, so a worktree under the scan root would surface as a bogus project card. Ordinary human-driven instances are unchanged — they still share the project's main checkout.
- A new per-project scheduler goroutine (~30–60s) drives auto-runs, distinct from the existing ~4s client-side fragment poll. It launches at most one *auto* run per project at a time; a manually-started AFK run is independent and additive, bounded only by `lab`'s global instance cap. Both kinds are reaped on PR-detected or timeout; a user-initiated Stop is neutral — it never counts as a failure and leaves the issue parked in `in-progress` for requeue.
- New persisted per-project state in `lab`'s store: `autoEnabled` and `consecutiveFailures`. In-flight runs are not persisted — they are re-adopted after a restart from their `<project>~<slot>~afk-<N>` session names, with the time-budget clock resetting.
